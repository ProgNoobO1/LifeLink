# LifeLink — Database Seeder Documentation

## Overview

This document explains how to bootstrap the **LifeLink Blood Management System** database with the full production-grade schema and realistic seed data for local development, testing, and demos.

> **Heads-up:** The Java servlets and DAOs in `src/main/java` currently target the **legacy** schema (`lifelink_database` with flat `users` / `blood_requests` / `donations` tables). The SQL files below define the **new normalised schema** (`lifelink_db`). You will need to refactor the Java models and DAOs to match these new tables before the application can read from / write to them.

---

## Files

| File | Purpose |
|------|---------|
| `db/schema.sql` | Creates the database, all tables, indexes, foreign keys, triggers, events, and stored structures. Run this **first**. |
| `db/seeder.sql` | Inserts sample lookup data, users, profiles, blood stock, requests, responses, donation history, audit logs, and notifications. Run this **second**. |

---

## Quick Start

### 1. Prerequisites

- **MySQL 8.0+** (or MariaDB 10.6+) running locally.
- A user with privileges to create databases, tables, triggers, and events (e.g. `root`).
- **Event scheduler** must be enabled (the schema script attempts to turn it on globally).

### 2. Run the Schema

```bash
mysql -u root -p < db/schema.sql
```

This creates:
- Database `lifelink_db`
- Lookup tables: `blood_groups`, `districts`
- Core table: `users`
- Profile tables: `donors`, `recipients`, `hospitals`
- Transaction tables: `blood_stock`, `blood_requests`, `request_responses`, `donation_history`
- Supporting tables: `blood_shortage_alerts`, `email_notifications`, `user_sessions`, `admin_activity_log`, `backup_log`
- Trigger: `trg_blood_shortage_alert` (auto-creates alerts when stock drops below threshold)
- Event: `evt_purge_expired_sessions` (daily cleanup of expired sessions)

### 3. Run the Seeder

```bash
mysql -u root -p < db/seeder.sql
```

### 4. Verify

```sql
USE lifelink_db;

SELECT 'Users'            AS table_name, COUNT(*) AS rows FROM users
UNION ALL SELECT 'Donors',  COUNT(*) FROM donors
UNION ALL SELECT 'Recipients', COUNT(*) FROM recipients
UNION ALL SELECT 'Hospitals', COUNT(*) FROM hospitals
UNION ALL SELECT 'Blood Stock', COUNT(*) FROM blood_stock
UNION ALL SELECT 'Requests', COUNT(*) FROM blood_requests
UNION ALL SELECT 'Responses', COUNT(*) FROM request_responses
UNION ALL SELECT 'Donations', COUNT(*) FROM donation_history;
```

Expected row counts:

| Table | Count |
|-------|-------|
| Users | 8 |
| Donors | 3 |
| Recipients | 2 |
| Hospitals | 2 |
| Blood Stock | 8 |
| Requests | 8 |
| Responses | 4 |
| Donations | 6 |

## Schema Reference (High-Level)

### Lookup Tables
- **`blood_groups`** — Normalised blood types (`A+`, `A-`, `B+`, `B-`, `AB+`, `AB-`, `O+`, `O-`).
- **`districts`** — Geographic locations with lat/lng for proximity search.

### Core & Profile Tables
- **`users`** — Single core table with `role` (`donor` | `recipient` | `hospital` | `admin`). Includes `is_active` and `is_approved` flags.
- **`donors`** — 1-to-1 extension for donors (availability, last donation, total donations, weight, etc.).
- **`recipients`** — 1-to-1 extension for recipients (medical notes, address, etc.).
- **`hospitals`** — 1-to-1 extension for hospitals (license, lat/lng, contact person, website).

### Inventory & Alerts
- **`blood_stock`** — Per-hospital, per-blood-group inventory with `low_stock_threshold`.
- **`blood_shortage_alerts`** — Auto-generated by trigger when stock drops ≤ threshold.

### Request & Response Flow
- **`blood_requests`** — Recipients create requests (status: `pending` → `accepted` / `rejected` / `completed` / `cancelled`).
- **`request_responses`** — Donors or hospitals respond to a request (`accepted` or `rejected`).

### History & Audit
- **`donation_history`** — Verified completed donations, linked to donor, hospital, and optionally the original request.
- **`email_notifications`** — Queue / log of system emails.
- **`user_sessions`** — Server-side session store with TTL.
- **`admin_activity_log`** — Audit trail of admin actions.
- **`backup_log`** — Tracks logical backup runs.

## Regenerating Password Hashes

If you want to add more users or change passwords, generate new BCrypt hashes:

```bash
# Using the project's existing dependency
cd target/BloodManagementSystem/WEB-INF/lib

# Quick one-liner via jshell (if available) or compile a small class
java -cp jbcrypt-0.4.jar org.mindrot.jbcrypt.BCrypt
# BCrypt.hashpw("myPassword", BCrypt.gensalt(12))
```

Or add a temporary main method to `PasswordUtil.java`:

```java
public static void main(String[] args) {
    System.out.println(hash("myPassword"));
}
```

## Resetting the Database

To wipe everything and start fresh:

```sql
DROP DATABASE IF EXISTS lifelink_db;
```

Then re-run:

```bash
mysql -u root -p < db/schema.sql
mysql -u root -p < db/seeder.sql
```

## Troubleshooting

| Issue | Solution |
|-------|----------|
| `Access denied` | Verify MySQL user credentials and that the account has `CREATE`, `TRIGGER`, and `EVENT` privileges. |
| `Event scheduler disabled` | Run `SET GLOBAL event_scheduler = ON;` as a MySQL super-user, or uncomment the line in `schema.sql`. |
| Trigger errors | Ensure you are running MySQL 8.0+; the trigger syntax uses `DELIMITER $$`. |
| FK constraint failures during seed | Make sure `schema.sql` ran successfully before `seeder.sql` — the seeder depends on the lookup tables existing. |
| App cannot connect | Update `DBConnection.java` to use `lifelink_db` instead of the old `lifelink_database`, and update the DAO queries to match the new column / table names. |

## Next Steps for Developers

1. **Update `DBConnection.java`** to point to `lifelink_db`.
2. **Refactor Models** (`User.java`, `BloodRequest.java`, etc.) to align with the new normalised tables.
3. **Rewrite DAOs** to join `users` with `donors` / `recipients` / `hospitals` as needed.
4. **Add new Servlets/JSPs** for the enriched features (inventory, shortage alerts, request-response flow, session table-backed auth).
